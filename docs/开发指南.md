# 开发指南：如何给本项目加功能（含踩坑经验）

> 这份文档写给「拿到这份源码、准备改它的人」。目标是：加一个新功能时，不用通读全部代码，
> 也能按既有模式在正确的位置落笔，并避开已经踩过的坑。
>
> 记录时间：2026-07（v1.0.9 之后）。文中 `文件:行号` 会随代码演进漂移，用方法名/关键字搜索定位更稳。

---

## 0. 先建立这个认知

本工程是**纯原生 Android**，没有任何第三方运行时依赖（HTTP 服务、JSON 修复、SSE 全部自己实现，
见 `app/build.gradle` 的 `dependencies {}` 为空）。所以：

- **不要引入 Retrofit / OkHttp / Gson 之类的库**。不是不能，是会给这个「单 APK、零依赖」的定位拆台；
  现有代码已经证明了自实现足够用（`HttpBridgeServer` 是手写的 socket HTTP 服务）。
- 所有功能都落在**四层之一**，加功能前先判断属于哪层，去对应文件「抄同层既有代码的结构」：

| 层 | 干什么 | 主文件 |
|----|--------|--------|
| UI 层 | 界面、开关、按钮、导航、PiP 按钮/悬浮球交互 | `MainActivity.java`、`FloatingBallView.java`、`Theme.java` |
| 服务层 | 前台服务、保活、通知、路由分发、上下文计数 | `ApiService.java`、`KeepAlive*.java`、`SystemReceiver.java` |
| HTTP 协议层 | HTTP 解析 + OpenAI 协议转换 | `HttpBridgeServer.java`、`OpenAiAdapter.java`、`PromptBuilder.java`、`LooseJson.java`、`ToolMarkup.java`、`ToolArgsFixer.java` |
| 页面注入层 | 在 chat.deepseek.com 页面里操作 DOM / 拦截 SSE | `app/src/main/assets/bridge.js` → `WebHost.java` → `DeepSeekController.java` |

数据流（改任何一层前先记住这条链）：

```
外部客户端 → ApiService.route() → handleChat() → DeepSeekController → bridge.js(页面内)
                                                                    ↓ onEvent 回传
外部客户端 ← OpenAiAdapter(转 OpenAI 协议) ← DeepSeekController.onJsEvent()
```

## 1. 工程结构地图（每个文件负责什么）

- `MainActivity.java` — 唯一的 Activity。控制台/对话页两个 Tab、所有设置项、PiP、悬浮球联动都在这里。
- `ApiService.java` — 前台服务。持有 `HttpBridgeServer`，实现 `route()` 路由、`handleChat()`、
  上下文计数、通知栏状态。**HTTP 接口的入口就在这个文件**。
- `HttpBridgeServer.java` — 手写 HTTP 服务：解析请求行/头/体，封装 `Request`/`Response`。
  只负责「把 HTTP 解析成对象」，不关心业务。
- `OpenAiAdapter.java` — OpenAI 协议适配：请求解析、响应拼装、SSE chunk、工具调用 `tool_calls` 生成。
- `PromptBuilder.java` — 把 OpenAI messages 拼成要注入官网输入框的提示词（含工具定义）。
- `ToolMarkup.java` / `ToolArgsFixer.java` / `LooseJson.java` / `JsonRepair.java` — 工具调用标记的
  解析、参数类型归一化、宽松 JSON 修复。**这块逻辑和桌面版 `Core/` 对齐，改之前先确认桌面版同名文件。**
- `DeepSeekController.java` — 原生 ↔ 页面的桥。单例；负责 `eval(js)` 注入、`callJs()` 阻塞等待、
  流式 `StreamListener`、以及把页面回传的 `onEvent` 事件分发给上层。
- `WebHost.java` — WebView 的静态持有者。**关键：WebView 挂在静态变量 `sWebView` 上，
  不随 Activity 销毁而销毁**（`detachFromParent()` 只把它从父布局摘下来，不 destroy）。
- `app/src/main/assets/bridge.js` — 页面脚本，暴露 `window.DSKB`（原生调用入口）和
  `window.DSB.onEvent`（回传入口）。
- `FloatingBallView.java` — 悬浮球自定义 View（含动效）。
- `KeepAlive*.java` + `SystemReceiver.java` — 保活：前台服务、无障碍兜底、JobService、开机自启。
- `Util.java` — 内存日志（`Util.log`，控制台「运行日志」看的就是它）、`prefs()`、md5/base64。

> ⚠️ `bridge.js` 在仓库里有两份：`app/src/main/assets/bridge.js`（Android）和
> `desktop/DSWebApi.Desktop/Assets/bridge.js`（Windows 桌面版）。**两份内容并不完全一致**，
> 改页面逻辑时若希望两端行为一致，记得两处都改、分别验证。

## 2. 构建与验证

标准构建（有网络时）：

```bash
./gradlew :app:assembleRelease      # 产物 app/build/outputs/apk/release/app-release.apk
./gradlew :app:assembleDebug        # 产物 app/build/outputs/apk/debug/app-debug.apk
```

**离线/受限环境**（本工程曾在无外网的沙箱里构建过，可用如下方式）：

```bash
./gradlew --offline assembleDebug
```

此时 `settings.gradle` 里加了本地 maven 仓库 `maven { url = uri('/opt/maven-repo') }`，
`build.gradle` 的 AGP 版本被降到本地缓存里有的版本（8.2.0）。如果你在正常联网环境开发，
**不要提交这些为离线而做的临时改动**（旁边留有 `*.orig` 备份文件，是当时被改前的原样）。

编译期注意：

- `app/build.gradle`：`minSdk 24 / targetSdk 34 / compileSdk 34`，Java 8。**API 24~34 都要能编译**。
- 用新 API 必须做版本判断（见 `MainActivity.buildPipParams()`：`Build.VERSION.SDK_INT >= 31` 才用
  `setAutoEnterEnabled`，`>= 26` 才用 `RemoteAction`）。老 API 用 `@SuppressWarnings("deprecation")`。
- 早期 Android 的方法引用/`try-with-resources` 已被 desugar，正常写即可。

验证闭环（务必做，别假设「应该没问题」）：

1. `./gradlew --offline assembleDebug` 必须 BUILD SUCCESSFUL；
2. 装到真机手点一遍改动路径（交互类功能必须真机验证，编译通过 ≠ 功能正确）；
3. 涉及 HTTP 接口的，用 `curl` 打一遍（见 README 里的示例）；
4. 涉及页面注入的，看「控制台 → 运行日志」（`Util.log`）确认没有异常。

## 3. 加功能：四个常见落点

### 3.1 加一个「设置项」（最常见）

设置项全在 `MainActivity.buildControlPanel()` 里，用 `makeSwitch / makeRow / makeRowCycle` 生成。

**开关（布尔值）**：

```java
set.addView(makeSwitch("开关名", "一句话说明", "your_key"));
```

- 默认值：`makeSwitch` 里的 `defOn` 判断决定默认开还是关（目前 `keep_screen / stateless /
  auto_newchat / pip_background` 默认开）。**若你的新开关默认应为「开」，把 key 加进那个判断**。
- 读取：`Util.prefs(this).getBoolean("your_key", 默认值)`。
- 即时生效：`makeSwitch` 的 `setOnCheckedChangeListener` 里已经有 `if ("key".equals(key)) ...` 的分支，
  照着 `pip_background` / `keep_screen` 的写法加一个分支。
- 存储 key 是裸字符串，**没有集中常量表**，新增时注意别和已有 key 冲突（全局搜一遍）。

**循环切换（枚举）**：`makeRowCycle("名称", "key", new String[]{"a","b"}, "说明")`。

**可编辑文本/数字**：`makeRow("名称", "key")`，然后**必须同时**在 `currentSetting()` 加一个
`case` 返回默认值、在 `putSetting()` 加解析分支（数字型要 `Integer.parseInt`），否则读到的会是空串。

> 经验：`currentSetting` / `putSetting` / `makeSwitch 的 defOn` 是**三个必须同步修改**的地方，
> 漏掉任何一个都会出现「默认值不对」或「改了不生效」的诡异现象。

### 3.2 加一个 HTTP 路由

在 `ApiService.route()` 里加判断即可，它就是个 `if` 链：

```java
if ("/v1/yourpath".equals(p)) {
    if (!auth(req, res)) return;              // 需要鉴权就加这行
    if (!"POST".equals(req.method)) { res.sendJson(405, errJson("Method not allowed", "invalid_request_error")); return; }
    // ... 业务 ...
    res.sendJson(someJson.toString());
    return;
}
```

- 鉴权用 `auth(req,res)`；返回错误用 `errJson(msg, type)`；响应统一 `res.sendJson(...)`。
- 想改动 `/v1/chat/completions` 的**行为**，落点是 `handleChat()` → `runBlocking()` / `runStream()`。
- 想改**协议字段**（多一个响应字段、改 chunk 结构），落在 `OpenAiAdapter`。
- 新增路由后记得在 `health()` 里按需暴露状态字段（可选）。

### 3.3 加一个「页面内动作」（bridge.js ↔ 原生）

这是本工程最有特色的部分：**原生不直接操作 DOM，而是把命令 eval 进页面，由页面的 `window.DSKB` 执行**。

三步：

1. **页面侧**：在 `app/src/main/assets/bridge.js` 的 `window.DSKB = { ... }`（约 714 行）里加一个方法：

   ```js
   myAction: function (o) {
     var r = doSomething(o);                       // 操作 DOM
     emit({ type: 'myEvent', reqId: o.reqId || '', ok: !!r, data: r });   // 回传给原生
   },
   ```

   回传统一走 `emit({type:...})` → `window.DSB.onEvent(json)`。

2. **控制器侧**：在 `DeepSeekController` 加调用方法。阻塞式等结果用 `callJs(name, arg, timeoutSec)`，
   流式/异步用 `eval(...)` + 在 `onJsEvent()` 里处理 `type`：

   ```java
   public JSONObject myAction(JSONObject arg) { return callJs("myAction", arg, 20); }
   ```

   `onJsEvent()` 里按 `type` 分发给 `StatusListener` / `StreamListener`，或直接处理。

3. **上层侧**：想暴露成 HTTP 接口就在 `ApiService.route()` 调它；想做成按钮就在 `MainActivity.onAction()` 加 case。

   > ⚠️ 页面里的对象是 WebView 的 JS 环境，**`eval` 必须在主线程 + WebView 已加载**。`DeepSeekController.eval`
   > 内部已经 `main.post(...)`，且空 webView 会静默返回，所以调用方不用自己判空，但要接受「页面没准备好时静默失败」。
   > 需要可靠结果就用 `callJs`（带超时，超时返回 `TIMEOUT`）。

### 3.4 加一个「画中画窗口按钮」或悬浮球行为

PiP 自定义按钮三件套（`MainActivity`）：

1. 常量：`ACTION_PIP_XXX = "com.hiweny.dswebapi.PIP_XXX"`；
2. `buildPipActions()` 里 `new RemoteAction(Icon.createWithResource(this, R.drawable.ic_xxx), "标题","说明", pipAction(ACTION_PIP_XXX, reqCode))`；
   图标放 `app/src/main/res/drawable/ic_xxx.xml`；
3. `registerPipActions()` 的 `onReceive` 里 `else if (ACTION_PIP_XXX.equals(a)) yourMethod();`，
   同时把 action 加进 `IntentFilter`。

悬浮球行为改 `ApiService.maybeShowFloatingBall()` 里 `FloatingBallView.Listener` 的 `onTap/onLongPress`。

> 注意：`RemoteAction` 是 **API 26+**；`enterPictureInPictureMode` 是 **API 24+**。
> 所有 PiP 新特性都要做版本判断，否则低版本机型直接崩。

## 4. 踩坑经验（PiP 后台保活这次，重点读）

背景：为了让 WebView 在退后台时不被 Chromium 节流，用 PiP 把窗口钉成「可见」。
`MainActivity` 里 `onUserLeaveHint()` 触发 `enterPip()`，PiP 窗口上放了一个「减号」按钮用来
「退出 PiP、缩成悬浮球」。

**坑 1：`moveTaskToBack(true)` 在 PiP 状态下基本不生效。**
一开始「减号」按钮的实现是 `setBallVisible(true)` + `moveTaskToBack(true)`，再延时 400ms 兜底 `finish()`。
实测多数机型下 PiP 状态里 `moveTaskToBack` 不退出 PiP，导致要不点两次、要不没反应。
**结论：退出 PiP 就直接 `finish()`。** 不要相信 `moveTaskToBack`。

**坑 2：`finish()` 退后台后，会被 autoEnter 立刻「弹回」画中画，形成退出即重进的死循环。**
这是 API 31+ 的 `setAutoEnterEnabled(true)` 干的：Activity 一进后台，系统又把它拉进 PiP。
**结论：退出前必须先关掉 autoEnter**，即 `setPictureInPictureParams(...setAutoEnterEnabled(false))`，
并用 `suppressPipUntil` 时间戳把 `onUserLeaveHint` 也一起压住：

```java
suppressPipUntil = SystemClock.uptimeMillis() + 2000L;
if (Build.VERSION.SDK_INT >= 31) {
    setPictureInPictureParams(new PictureInPictureParams.Builder()
            .setAspectRatio(pipAspect()).setAutoEnterEnabled(false).build());
}
finish();
```

`onResume()` 里会重新 `applyPipParams()` 把 autoEnter 打开，所以只影响这一次退出。

**坑 3：Activity 销毁 ≠ WebView 销毁。**
`finish()` 会走 `onDestroy()`，那里调用了 `WebHost.setActivity(null)` 和 `WebHost.detachFromParent()`。
但 `WebView` 本身是 `WebHost.sWebView` 这个**静态字段**持有的，只是被从父布局摘下来，**没有被 destroy**。
所以「退出 PiP → 悬浮球 → 点球重新进 PiP」这条链里，页面状态、登录态、正在进行的流都不会丢。
—— 这是本工程「保活」设计的基石，改 `WebHost` 时要格外小心别把 `destroy()` 误加到这条路径上。

**坑 4：系统 ✕ 关闭 PiP 走的是另一条路径，必须单独兜底。**
用户点 PiP 窗口的系统关闭按钮时，Activity 被销毁，**并不会**经过我们的「减号」方法，
此时悬浮球还是隐藏状态，用户再也叫不出球。**结论：在 `onDestroy()` 里补一句**
`if (inPip) setBallVisible(true);`（`setBallVisible` 内部受 `floating_ball` 开关约束，开关关着时无副作用）。

**坑 5：`enterPictureInPictureMode` 在窗口没就绪时会被系统拒绝。**
所以有 `enterPipWhenReady(retries)` 做 250ms 延时 + 重试；`enterPip()` 里如果返回 `false`
要把 Tab 切回去，避免界面停在错误状态。

**坑 6：自己拉起外部 Activity（文件选择器、系统设置）会误触发 `onUserLeaveHint`。**
所以有 `startExternal()`：跳转前设 `suppressPipUntil`，并临时关掉 autoEnter。**以后凡是
「从 App 里 startActivity 到别处」，一律走 `startExternal()`，不要直接 `startActivity()`。**

**通用教训**：

- PiP / 悬浮窗 / 前台服务这类**系统级交互，编译通过不代表行为正确**，必须真机验证，
  而且要覆盖：点减号、点系统✕、点悬浮球、按 Home 键、息屏来电 这几条路径。
- 版本分叉多（API 24/26/31/33），**每个特性都要问一句「低版本会不会崩」**。
- 用 `Util.log()` 埋点，出问题时看控制台「运行日志」，比盲猜快得多。

## 5. 提交前自查清单

- [ ] 新代码只改了必要的部分，没有顺手重构无关代码 / 没有引入新依赖；
- [ ] 新 API 有版本判断，`minSdk 24` 不会崩；
- [ ] 新增设置项：`currentSetting` / `putSetting` / `defOn` 三处同步改过；
- [ ] 新增 HTTP 路由：加了 `auth`、处理了非 POST、错误用 `errJson`；
- [ ] 改了 `bridge.js`：Android 和 Desktop 两份都考虑过是否要同步；
- [ ] `./gradlew --offline assembleDebug` 通过；
- [ ] 真机手动走查了改动路径（交互类功能必做）；
- [ ] 没有把「为离线构建而改的」`settings.gradle` / `gradle.properties` / `build.gradle` 一起提交。
